# 비회원 체험 API 및 적용 상태

## 현재 상태

프론트엔드와 Muneo-Server 체험 API 구현을 완료했다. 사용자의 백엔드 변경 승인 후 정확한 체험 경로의 인증 정책과 Redis 보관·호출 제한을 적용했다. 배포 대상 백엔드는 기존 로컬의 MaxedOut-Muneo 저장소가 아니라 최신 Muneo-official/Muneo-Server다. 운영 반영에는 두 저장소의 변경을 함께 배포해야 하며, **응답 형식이 바뀌는 변경은 백엔드를 먼저 배포한다.** 새 프론트는 새 응답 필드가 없으면 결과를 그리지 못한다. 샘플 분석을 실제 결과처럼 보여주는 폴백은 없다.

## 사용자 흐름

체험 화면은 로그인 후 서비스와 같은 사이드바 레이아웃·입력·로딩·결과 컴포넌트를 쓴다. 다른 점은 입력 화면 상단의 체험 안내 한 줄과, 결과에서 **대표 공정 하나만 열려 있고 나머지가 잠겨 있다**는 것뿐이다.

- `/try/analysis`: 공사 정보·파일 입력 → 실제 진단 요청 → 상단 건수 카드는 전체 기준, 대표 공정 하나의 진단 항목 전체 공개. 나머지 공정은 이름과 확인 필요 건수만 보이고 내용은 흐린 가짜 행으로 잠긴다.
- `/try/estimate`: 기존 3단계 조건 입력 → 실제 가견적 요청 → 입력 요약·적용 보정·참고 사례 수와 대표 공정 하나의 금액·세부 항목 공개. 나머지 공정의 금액·세부 항목, 공정별 합산의 잠긴 행, 총 견적 범위는 잠긴다.
- 대표 공정은 서버가 고른다. 진단은 누락 3·불분명 2·중복 1 가중치 합이 가장 큰 공정(같으면 항목이 많은 공정), 가견적은 데이터 부족 공정을 빼고 참고 사례가 있는 세부 항목이 가장 많은 공정(같으면 항목 수, 최대 금액 순)이다.
- 로그인·회원가입·카카오 인증 후 `/analysis/trial` 또는 `/estimate/trial`에서 동일한 전체 결과를 조회한다. 같은 레이아웃에서 흐림이 걷히며 나타난다. 재업로드·재분석하지 않는다.
- 전체 결과는 기존 이력 저장 API로 사용자가 직접 저장한다.
- 취소·오류 시 현재 탭의 입력과 파일을 유지한다. 새로고침 후에는 서버가 보관 중인 완료 결과를 복원한다. 작성 중인 파일은 새로고침하면 다시 선택해야 한다.

## 엔드포인트

모든 브라우저 요청은 기존 Next.js `/api/[...path]` 프록시를 경유한다.

| 경로                               | 인증 | 역할                                                       |
| ---------------------------------- | ---- | ---------------------------------------------------------- |
| `GET /api/v1/trials/analysis`      | 공개 | 체험 쿠키 발급, 저장된 부분 결과 조회. 없으면 204          |
| `POST /api/v1/trials/analysis`     | 공개 | 기존 분석 API와 같은 multipart 필드. 부분 결과만 반환      |
| `GET /api/v1/trials/estimate`      | 공개 | 체험 쿠키 발급, 저장된 부분 결과 조회. 없으면 204          |
| `POST /api/v1/trials/estimate`     | 공개 | 기존 가견적 생성 JSON 입력. 부분 결과만 반환               |
| `GET /api/v1/trials/{kind}/result` | 필수 | `{ input, result }` 전체 결과. 최초 로그인 사용자에게 귀속 |

부분 응답의 타입은 `apps/web/src/api/trial/types.ts`에 정의되어 있다. 공통으로 `kind`, `expiresAt`을 보낸다.

- 진단: `report`(업체명·평수·분석일·공사 정보와 대표 공정 하나의 `process_sections`), `sections`(원래 순서의 전체 공정 `id`·`display_name`·`itemCount`·`counts`·`locked`), `counts`, `totalItems`.
- 가견적: `input`(사용자가 입력한 조건), `result`(선택 공정·시공범위·보정·참고 사례 수·데이터 부족 공정, 대표 공정과 데이터 부족 공정의 금액·세부 항목만), `revealedProcess`, `lockedProcesses`(`name`·`itemCount`·`priced`).
- 잠긴 공정의 금액·세부 항목·진단 내용, 총 견적 범위, 참고 사례 목록, 검색 쿼리, 가견적 저장 토큰은 비회원 응답에 넣지 않는다. 화면의 흐린 행은 프론트가 만든 가짜 값이며 CSS로 실제 값을 가리는 방식이 아니다.
- 업체명과 가견적 입력 조건은 같은 체험 쿠키를 가진 브라우저가 직접 보낸 값이라 응답에 포함한다. 결과 화면 상단과 입력 요약을 로그인 후 화면과 똑같이 그리고, 새로고침 후에도 복원하기 위해서다.
- 배포 전환용으로 이전 필드(`firstItem`, `totalProcesses`, `firstProcess`)도 대표 공정 기준으로 함께 보낸다. 새 프론트는 이 필드를 쓰지 않으며, 이전 형식으로 보관된 결과는 `isTrialPreview`로 걸러 새로 체험하게 한다. 이전 프론트가 모두 내려간 뒤 제거할 수 있다.

## 백엔드 적용 범위

- 무작위 `muneo_trial` 쿠키: HttpOnly, Secure, SameSite=Lax, Path=/, 30분. 토큰을 URL·localStorage에 넣지 않는다.
- Redis에 입력과 전체 결과를 30분 보관한다. 업로드한 파일 바이너리는 이 체험 저장소에 보관하지 않는다. 기존 AI 서비스의 원본 파일 처리 정책은 별도다.
- 공개 허용은 표의 정확한 GET/POST 네 경로에만 적용한다. 전체 결과·저장·이력 API의 인증은 유지한다.
- 동일 세션·종류의 중복 분석은 409로 차단한다. 기본 한도는 세션당 30분에 3회, 서비스 전체 1시간에 60회다. `TRIAL_SESSION_LIMIT`, `TRIAL_GLOBAL_HOURLY_LIMIT`으로 조절할 수 있다. 쿠키 재발급으로 전체 한도를 우회할 수 없으며, 초과 시 AI 호출 전에 429를 반환한다. 실패한 AI 호출도 한도에 포함된다.
- 첫 전체 결과 조회에서 로그인 사용자 ID를 원자적으로 귀속한다. 다른 계정은 403, 결과 만료는 410, 미로그인은 401이다. 모든 체험 응답은 `Cache-Control: no-store`다.
- 파일은 최대 5개, 각 10MB, 합계 20MB로 제한한다. 기존 회원 업로드를 유지하기 위한 Spring 전역 설정은 파일당 20MB, multipart 헤더를 포함한 요청 전체 21MB이며 체험 한도는 컨트롤러에서 별도로 검사한다. 용량 초과는 413과 공통 `ApiResponse` 오류 형식을 반환한다.
- 작업별 잠금 토큰을 확인해 취소·시간 초과 후 늦게 도착한 이전 요청이 새 결과나 잠금을 덮어쓰지 못하게 한다. Redis 장애 시 AI 호출을 시작하지 않는다.
- 최신 AI의 가견적 저장 토큰은 체험 세션 ID로 발급하고 MongoDB 임시 보관 기간을 30분으로 맞춘다. 로그인 계정이 Redis 결과 소유권을 얻으면 해당 토큰 소유자도 이전한다. 기존 토큰 저장 API를 그대로 사용하며, 이미 소비된 토큰은 재생성하지 않는다.
- 체험 실패 응답은 기존 API와 같은 `{ success, status, code, timestamp, message }` 형식을 사용한다. 필드 검증 오류가 있으면 `error`가 추가된다.

## 검증 구분

프론트엔드 E2E는 백엔드와 같은 공개 규칙을 따르는 모의 API로 대표 공정 공개·잠긴 공정 비노출, 실제 로딩 화면, 입력 보존, 결과 복원, 로그인·가입·카카오 복귀, 만료 안내, 화면 폭을 검증한다. 백엔드 통합 테스트는 실제 HTTP 서버·로그인/JWT·Redis로 동일 결과 조회, TTL, 계정 귀속, 동시 요청과 한도를 검증한다. AI 응답과 MongoDB 토큰 이전은 대체하고, 토큰 이전 쿼리와 만료 정책은 별도 단위 테스트로 검증한다. 운영 AI 품질·응답 시간이나 운영 배포 완료를 의미하지 않는다.

Muneo-Server에서 전용 로컬 Redis 포트를 지정해 `TRIAL_TEST_REDIS_PORT=16389 ./gradlew test`로 통합 테스트를 실행한다. 현재 운영 백엔드 저장소에는 자동 배포 워크플로우가 없으므로 기존 서버 배포 절차를 확인해야 한다. 테스트 포트에 운영 Redis를 지정하지 않는다.
